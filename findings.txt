[2026-10-05] API / in-process harness - first social-mix benchmark
Source: loop-metrics.txt
Setup:  scripts/load-test.ts, mixed feed/post/like/follow, concurrency 10-500,
        no server cache.
Result: throughput rose to 1052 rps at concurrency 200 (avg 178 ms, p95 267 ms),
        then fell: 920 rps at 500 (avg 509 ms, p95 770 ms).

        request-shape problem, not load. See the 2026-10-12 follow-400 entry.

[2026-10-12] k6 staged suite - follow 400s fixed, then 500/2000 VU runs
Source: traffic-metrics-12-10-2026.txt
Setup:  120s staged suite (ramp, peak, fluctuate, ramp down), mix feed 70 /
        follow 15 / like 10 / post 5, 1-5s think time, 10s feed cache, /feed.
Result: before the fix (500 VUs): ~15% failed, all HTTP 400 (2041 of 13914).
        after the fix (2000 VUs): 0.07-0.09% failed, only 409s (a user
        following someone twice or liking twice), which are expected.
        2000 VU runs: 467-474 RPS, p50 8-12 ms, p95 ranged 45.8 / 111 / 164 /
        243 / 268 ms across five runs, max ~460-900 ms.
        Feed cache hit rate: ~15% at 500 VUs, ~41% at 2000 VUs.
Helped: the fix in commit e2e98e9 removed the 400s (Fastify rejects an empty
        body sent as application/json; follow requests now send no content-type).
        Earlier files show similar steady ~8-15% failures, probably the same
        cause, but their failure breakdown was not recorded, so unconfirmed.
Did not: DB pool 17 vs 50 made no consistent difference at 2000 VUs.
        Pool 50 runs: p95 45.8 and 164 ms. Pool 17 runs: 243, 111, 268 ms.
        The spread within one setting is as big as the spread between them.
Caveats: p95 varies about 6x between identical setups, so one run proves
        nothing. Use several runs and compare medians.
        The old numbers above were taken on the original dataset and with the
        in-memory cache starting cold or warm unpredictably; restart the API
        between runs.

[2026-10-13] UI - 5-minute per-post cache, paging, media loading
Setup:  React + Vite app in frontend/, proxy /api to 127.0.0.1:3000.
Helped:
  - Pages of 20; next page requested when the 15th post of the latest page is
    visible, so it arrives before the user hits the bottom.
  - Client keeps each post for 5 minutes. Going to a profile and back restores
    the feed and scroll position without refetching.
  - Videos: preload="none" at first, then the load starts ~1500px before the
    video is on screen (so it is ready on arrival), and play/pause follows
    visibility. Images use loading="lazy" with fixed aspect ratios, so layout
    does not jump (CLS 0 in the profile below).
  - content-visibility: auto on posts (skip layout/paint off-screen).
Did not:
  - Plain preload="none": videos only began loading when they reached the
    screen, which showed as a start delay. Replaced by the lookahead above.
Caveats / open:
  - Not measured: how much content-visibility helped. No before/after was taken.
  - List virtualization not implemented (adds a dependency and would unmount
    preloaded videos). Revisit only if a profile of a very long feed shows jank.
  - Image and video bytes are served by third parties and are not part of any
    load test; k6 only fetches the URLs.

[2026-10-13] UI - DevTools Performance profile, ~13 s of very fast scrolling
Result: range 13.25 s. System 754 ms, Painting 399 ms, Rendering 372 ms,
        Scripting 201 ms. First-party main-thread time 80.9 ms (localhost).
        3rd party imgsrc.pub: 62.5 kB transferred. CLS 0. LCP and INP not
        captured. JS heap 113 MB, fluctuating (normal GC plus video buffers).
Helped: nothing to fix on performance; the main thread was mostly idle.
Did not: n/a for performance.
BUG FOUND: scrolling fast to the end sometimes did not load the next page; the
        user had to scroll up and down again.
  Cause: the next-page trigger watched one element (15th post of the latest
        page) and only fired on a visibility change. A fast fling can skip it,
        and a trigger that fires during an in-flight request is ignored.
  Fix:  added a bottom sentinel (1000 px lookahead) that is re-checked after
        every load, so being near the bottom triggers a load without a new
        crossing. It stops on error, so a failing API is not hit in a loop.
Open:   fix not yet confirmed in a browser. Re-test with repeated fast scrolls
        to the bottom. Record memory after ~500 posts, and capture a profile
        with and without content-visibility for a real comparison.

[2026-10-13] Data / API - stored counters for follows, posts and likes
Why:    profiles recomputed follower, following and post counts with COUNT(*)
        subqueries on every view; cost grows with follower count.
Change: users.follower_count / following_count / post_count and
        posts.like_count (INTEGER NOT NULL DEFAULT 0). Follow, unfollow, create
        post and like now run in one transaction with their counter update, and
        change the counter only when a row was really inserted or deleted (a
        duplicate follow/like returns 409 and does not double count). Follow
        and unfollow update both user rows in one statement so crossing
        follows lock rows in the same order. Profile reads the stored values;
        /home-feed and /users/:id/posts return likeCount. /feed unchanged.
        Seed recomputes counters at the end; `npm run seed -- --counters-only`
        repairs them from the rows.
Result: backfill on the existing data corrected user counters and ~259k post
        like counts. After that, a full recount found 0 drifted users and 0
        drifted posts, before, during and after 1,560 concurrent follows and
        1,560 concurrent unfollows between 40 users in both directions: no
        deadlocks, no drift. Duplicate follow/like -> 409, repeat unfollow ->
        404, counters unchanged.
Did not / unknown:
  - Load impact NOT measured yet. The k6 follow (15%), like (10%) and post (5%)
    actions are now transactions with extra UPDATEs, so staged-suite numbers
    will differ from every earlier entry. Re-baseline before comparing.
  - Hot rows: a user with very many followers serialises on its counter row.
    Fine for this data (no celebrities); would need sharded counters otherwise.
  - Counters can still drift if rows are changed outside the routes (manual SQL,
    bulk seed); recompute with --counters-only.
Side effect of the test: the concurrent unfollow step also removed 11 follow
        rows that already existed between users 200-239 (not recorded, so not
        restored). Seed data only.

[2026-10-12 21:30 UTC] k6 staged 2000 VUs - repeat run and first diagnosis
Source: traffic-metrics-13-10-2026.txt (second entry)
Result: run 2 of the same config was worse again: 36,059 requests, 292.78 RPS,
        avg 2003 ms, p50 2364 ms, p95 4571 ms, max 5338 ms, 0.07% failed (409s
        only), cache hit 27.7%.
        Summary of the three runs of this config: 11:05 p95 268 ms / 468 RPS;
        21:26 p95 3417 ms / 381 RPS; 21:30 p95 4571 ms / 293 RPS.
        The slowdown reproduces, so it is not one-off noise, and it got worse
        between consecutive runs (data written by each run, warm-up state, or
        machine load are possible reasons; not determined).
Checked at idle after the runs (everything fast, Postgres 0.4% CPU, 533 MiB):
  - Single requests: /feed miss 37 ms, /home-feed 18 ms, follow 60 ms,
    unfollow 39 ms, health 4 ms (one sample each).
  - Counter cost, measured directly (200 follow+unfollow pairs): old shape
    8.4 ms, in a transaction without counters 10.5 ms, with counters (current)
    8.8 ms. A SELECT 1 round trip is 0.7 ms. So the counter UPDATEs and the
    extra BEGIN/COMMIT cost ~0 at idle; 0 drift after the bench.
  - /feed posts query, EXPLAIN ANALYZE (users 777 and 2500): 14-15 ms
    execution. About 1,100-1,700 posts rows are read via bitmap scan and
    sorted; a hash join builds a hash of all 26,000 users every call (~8 ms
    of the plan). Forcing index nested loops on users: median 10.9 ms vs 14.8
    ms default. So the join is ~4 ms of ~15; reading the followed users'
    posts is the rest and is inherent to the query.
  - users table is now 3.8 MB (was 1.6 MB): three counter columns plus dead
    rows from the backfill. posts is 132 MB.
Meaning: one cache-missing /feed costs ~11-15 ms of database CPU. At ~275
        misses/s (33k feed requests, 36% hit rate, in 120 s) that is
        3-4 CPU-seconds per second, which can saturate a small Docker VM and
        queue everything, including the cache hits behind the pool. This is a
        plausible bottleneck, but it is a hypothesis: there is no 11:05
        measurement of the same query, and DB CPU was not sampled during the run.
Not shown: that the counters caused the slowdown. Their write cost is ~0 at
        idle. Under heavy concurrent load a longer-held connection could still
        matter (4 round trips per follow instead of 1); untested.
Next:   (1) A/B on identical data: run the same suite against the previous
        commit's code (counters off) and compare; (2) sample CPU of the
        Postgres container and node during a run (docker stats every few
        seconds); (3) add per-action latency to the k6 output.
